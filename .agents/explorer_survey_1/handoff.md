## 2. Logic Chain

1. From **Observation 1**, `action` is a composed partial that expands into an HTML `<form>`, two `<input type="hidden">` fields, and one `<button>`.
2. From **Observation 1 and 2**, `action` requires 5 arguments: 1 positional button label (`content`) and 4 keyword modifiers (`to:`, `path:`, `return_to:`, `variant:`).
3. From **Observation 2 and 3**, the `path:` and `return_to:` arguments reflect specific payload requirements of the dashboard workspace item triage. Because these fields are hardcoded in `action.sp`, when `dormant.sp` required an additional payload parameter (`status: "dormant"`), `action` could not be used and had to be rewritten as a custom form partial.
4. From **Observation 4 and 5**, the language runtime and grammar checkers enforce this exact signature: `check_shape.rb` shows it is the longest sentence in the language (5 arguments vs 1.28 average), and `check_grammar.rb` strictly enforces the 4 modifiers declared in `action.sp` against any call site and against `VOCABULARY.md`.
5. Therefore, the 5-argument sentence is an architectural symptom of leaking a specific form payload and UI layout into a single rigid inline macro, rather than composing general-purpose primitives (`form`, `actions`, `button`, `hidden`).

## 4. Conclusion

The `action` primitive is currently a vocabulary partial (`lib/vocabulary/action.sp`) functioning as a brittle, 5-argument macro for a single-button POST form. It suffers from:
1. Longest sentence length in the language (5 arguments).
2. Domain parameter leakage (`path:`, `return_to:`).
3. Inflexibility (cannot support variable hidden inputs like `status:` in `dormant.sp`).

The abstraction can be refactored either by:
- Enabling block children for `action` or `form` to enclose payload definitions (e.g. `action "Commit", to: "/actions/commit", variant: primary do ... end` or `actions do action "Commit", to: ... end`).
- Composing with the existing `actions` container (`lib/vocabulary/actions.sp`) and `button` primitive with `formaction:` or nested hidden fields.
- Allowing `action` to derive hidden inputs from an enclosing or passed subject.
